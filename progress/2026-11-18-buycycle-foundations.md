## 실제 학습한 내용

이 문서는 ChatGPT가 제공한 읽기 중심 강의의 학습 범위를 요약합니다. 아래 개념 설명과 예시는 학습자 본인의 설명이나 이해도 검증 결과가 아닙니다.

### Python 기초
- 변수는 값을 참조하는 이름이고 `=`는 할당입니다. `int`, `float`, `str`, `bool`, `list`, `dict`의 용도와 조건문·반복문을 다뤘습니다.
- `return`은 함수의 결과를 호출자에게 전달하고, `print`는 출력만 수행합니다.
- 원화 단위 금액의 정수 표현과 십진 계산이 필요한 경우의 `Decimal`을 구분했습니다.
- `build_plan(holdings, prices, targets, cash)`처럼 외부 I/O를 분리한 계산 함수를 순수 함수의 예로 살펴봤습니다.

### 알고리즘과 테스트
- 제약 조건(현금 초과 금지, 음수 수량 금지)과 목적 함수(목표 비중과의 오차 최소화)를 구별했습니다.
- Buycycle의 1주씩 제곱오차 개선 방식은 탐욕 알고리즘이며, 일반적으로 전역 최적성을 보장하지 않습니다. 소형 입력을 전수 탐색해 결과를 비교하는 방법을 학습했습니다.
- 단위·통합·종단간·회귀 테스트, 경계값 분석, 속성 기반 테스트의 목적을 다뤘습니다.
- 핵심 검증 후보: `sum(quantity * price) <= cash`, 매수 수량은 0 이상의 정수, 동일 입력에 대한 결정적 결과, 주문이 없는 상태와 경계값.

### 상태와 데이터베이스
- 주문 생성, 접수, 부분 체결, 전량 체결, 취소, 거부, 상태 불명확 등의 상태와 허용 전환을 구분하는 상태 머신 개념을 학습했습니다.
- SQLite의 영속성, 테이블/키, 트랜잭션의 ACID 성질과 유니크 제약을 다뤘습니다.
- DB 커밋과 증권사 주문은 하나의 원자적 트랜잭션으로 처리되지 않습니다. API 응답 실패가 주문 실패를 의미하지 않을 수 있어 외부 주문 조회와 대조가 중요합니다.
- 월별 정기 매수의 실행 키와 수동 매수 요청별 키를 구분해야 합니다. 체결 기록만으로 중복 실행을 판단하면 미체결 주문을 놓칠 수 있습니다.

### 아키텍처 기초와 심화
- 모듈의 책임, 응집도·결합도, 변경 영향 범위를 평가하는 방법을 공부했습니다.
- 추상화는 사용자가 알아야 할 계약을 드러내고 구현 세부를 감추며, 캡슐화는 내부 상태 변경 경계를 관리합니다.
- 의존성 주입(DI)은 객체를 외부에서 전달하는 기법이고, 의존성 역전(DIP)은 상위 정책이 구체 기술 구현에 종속되지 않도록 하는 원칙입니다. `Protocol`과 테스트 대역을 예로 살펴봤습니다.
- 계층형·헥사고날·클린 아키텍처, SOLID, YAGNI를 비교했습니다. 현재 Buycycle은 단순한 계층 구조를 기본으로 하고 브로커 같은 외부 접점에만 포트/어댑터 개념을 선택적으로 적용하는 판단을 학습했습니다.
- API 서버와 OS 스케줄러가 실행하는 작업 프로세스를 분리하더라도 공유 DB와 외부 주문에 대한 동시성 및 멱등성 통제가 별도로 필요합니다.
- Claude Hook은 강제 자동화의 이익과 비용을 비교해 도입하며, 로그 Hook 제거는 기록 책임을 기능 단위 문서와 Git으로 나누는 사례로 살펴봤습니다.

## 이해가 확인된 설명·판단과 근거

- 학습자가 독립적으로 작성한 개념 설명, 코드 해석, 설계 판단 및 실제 테스트 결과는 이번 대화에서 확보되지 않았습니다.
- 따라서 관련 개념의 `verified_level`은 0으로 유지합니다. AI가 설명한 사례를 학습자의 검증 근거로 기록하지 않습니다.
- Buycycle 최신 커밋의 설계 검토는 실제 코드 실행 검증과 구분합니다.

## 아직 확인하지 못한 내용

- Python 자료형, 변수 참조, 함수 호출의 독립적 코드 해석 능력
- 탐욕 알고리즘과 전수 탐색을 비교하는 구현·테스트 능력
- 주문 상태 모델·트랜잭션·멱등성 설계 대안에 대한 독립적 판단
- 모듈 경계, 의존성 방향, DI/DIP 및 SOLID를 실제 코드에 적용하는 능력

## 추가 학습·보류 주제

- Buycycle의 첫 계산 함수가 구현되면 실제 입력 → 계산 → 반환 경로를 코드와 테스트로 추적
- 주문 구현 전 주문 접수·부분체결·응답 유실·재실행을 포함한 상태 전환표와 테스트 작성
- 작은 규모의 탐욕 알고리즘 결과를 전수 탐색과 비교
- 아키텍처 판단은 실제 파일과 diff가 생겼을 때 변경 영향 범위를 근거로 재검토
- 요구가 발생하기 전에는 추가 Hook, 다중 에이전트, 무거운 추상화 도입 보류

## 실제 적용

- 이번 세션에서 제품 코드의 작성·실행·테스트는 하지 않았습니다.
- 제품 관련 설계 문서의 검토와 이론 학습만 수행했습니다. 사례(case)와 포트폴리오 근거는 아직 등록하지 않았습니다.
