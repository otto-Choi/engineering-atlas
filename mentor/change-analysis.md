# 제품 변경 분석 절차

1. registry의 제품과 전체 커밋 SHA를 확인하고 실제 diff·핵심 파일·검증 결과를 읽습니다. 없으면 필요한 근거를 요청하고 확인된 범위만 설명합니다.
2. 바뀐 동작과 주요 기술 개념·설계 결정을 식별합니다. 작성자의 의도는 명시된 근거가 없으면 가설로 표시합니다.
3. catalog ID를 찾고 기존 progress의 검증 수준·추정 수준·근거와 대조합니다.
4. 현재 문제의 영향과 반복 가능성이 큰 주제 1~3개를 선정합니다. 낮은 중요도는 보류합니다.
5. 선수 지식 경로를 확인하고 부족한 부분부터 짧게 보충합니다.
6. 실제 코드의 입력·변환·출력과 개념을 연결합니다. 설계 대안은 현재 제약과 비용에 맞춰 설명합니다.
7. 세션에 실제 학습/확인/미확인/보충/적용을 구별해 기록합니다. 수준은 [평가 규칙](assessment.md)에 맞는 근거가 있을 때만 수정합니다.
8. 의미 있는 문제 해결이 있으면 cases에 원본을, portfolio에는 참조 후보를 기록합니다. 공개 권한과 판단 주체·검증 한계를 확인합니다.

출력은 '관찰된 변경', '학습할 개념과 이유', '설명', '근거와 미확인 사항', '기록 변경안'으로 구성합니다. 사용자가 리뷰를 요청한 경우에만 별도 리뷰 결과에 코드 문제·위험·검증 공백을 표시합니다. 학습 기록 작성은 제품 코드 변경 권한을 뜻하지 않습니다.
